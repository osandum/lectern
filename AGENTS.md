# AGENTS.md

Guidance for coding agents working in this repository.

## What this is

Lectern: a read-only, [Papers](https://apps.gnome.org/da/Papers/)-style Markdown viewer for GNOME. Open a `.md` file, read/search/zoom/print it — no editing UI. One window per opened file, no sidebar (deliberate departures/similarities to Papers/Evince, not accidents).

## Commands

```sh
# Setup (once) -- --system-site-packages is required: PyGObject/GTK4/Libadwaita
# come from system packages, not pip, and the venv needs to see them.
python3 -m venv .venv --system-site-packages
source .venv/bin/activate
pip install -e .

# Run
lectern path/to/file.md

# Test (headless, no display needed -- see Architecture below)
pytest tests/
pytest tests/test_renderer.py::test_bold_produces_strong_tag  # single test

# Manual smoke test fixture exercising every Markdown feature:
lectern tests/fixtures/kitchen_sink.md
```

There is no linter or formatter configured in this repo.

## Architecture

**Rendering is native GTK widgets, not HTML.** A single `Gtk.TextView` + `Gtk.TextBuffer` with `Gtk.TextTag`s does all inline/block formatting. This was a deliberate choice over embedding WebKitGTK — benchmarked and rejected because loading even trivial HTML in WebKit cost 300ms+, which conflicts with the "feels instant" launch goal. The only widgets embedded in the buffer (via `Gtk.TextChildAnchor`) are table grids and `hr` separators.

**Critical, non-obvious GTK behavior:** `Gtk.TextView` never stretches an anchored child widget to fill the line — `hexpand`/`halign` on the widget are silently ignored, no matter how they're set. This bit us once already (tables/hr rendering narrow and non-responsive to resize). The fix, and the pattern to follow for any future anchored widget: track it and actively push a width onto it via `window.py`'s `_sync_fill_width_widgets`, driven by the `TextView`'s `hadjustment` `page-size` (the one reliable signal for "the view's content width changed" — `Gtk.Widget` has no public size-change signal in GTK4).

**Module responsibilities:**
- `document.py` — file I/O + Markdown parsing (`markdown-it-py` + `mdit-py-plugins` for GFM tables/strikethrough/footnotes/tasklists). Imports of `markdown_it`/`pygments` are deliberately deferred into function bodies here and in `highlighting.py`, not at module top level — a bare `lectern` launch or an argument error shouldn't pay for parsing/highlighting machinery it never uses.
- `renderer.py` — walks the `markdown_it.tree.SyntaxTreeNode` tree into the `Gtk.TextBuffer`. Every block-level emission *also* appends a `PrintItem` to `self.print_model` in the same pass. This dual-write exists because `Gtk.TextChildAnchor`-embedded content (tables) is invisible to buffer-native search and can't be reconstructed by re-walking the buffer afterward (it's a single object-replacement character in the text stream) — `printing.py` works off `print_model` exclusively, never off the live buffer.

  **Inter-block spacing is a CSS-style collapsed-margin model**: the gap before block B is `max(bottom(A), top(B))`, applied as a `pixels-above-lines` tag on B's first line, because GTK's above/below margins *add* where CSS's collapse. Two consequences worth knowing. `_prev_block_bottom` and `_prev_block_padding` must be read **before** dispatching a block — walking a container runs its children through the same method, so reading them back afterwards yields whatever its last child owed. And **tight vs loose lists are honoured** (`_block_bottom_margin`): a list with no blank lines between its items is *tight*, markdown-it emits no `<p>` for such items and flags their paragraphs `hidden`, and no `<p>` means no box to carry a margin — so tight items pack at `LIST_ITEM_GAP` while loose ones get a full paragraph margin. A *nested* list owes nothing below itself either, matching GitHub's `ul ul { margin-top: 0; margin-bottom: 0 }` — which is why the item *following* one takes its gap from its own top margin instead (`_list_item_top_margin`, GitHub's `li > p { margin-top: 16px }`). Miss that and a loose list collapses to the bare item gap coming out of every sublist: 1.75em against the browser's 2.5em. Before any of this, every item was treated as loose, which is what pushed nested lists a full em away from the parent item they belong to (#16).
- `tags.py` — the single source of truth for `Gtk.TextTag` style properties (`tag_style_props`), consumed by both the live buffer (screen) and `printing.py` (paper), so the two can't visually drift apart. Also owns light/dark palettes and the two in-place update passes over a built table, which are deliberately disjoint and compose in either order: `update_tag_colors` (colors only, on theme change) and `apply_metrics` (lengths only, on zoom or content-column change). Every length there is written in nominal 96dpi pixels against `BASE_FONT_PX` — i.e. correct as written only at 100% zoom with an uncapped column.

  **A `Gtk.TextView` has no line-height**, and that turned out to be behind a whole class of "the spacing feels tight" complaints. Its lines are as tall as the font makes them (19px for 16px Adwaita Sans) where CSS pads every line box out to `line-height: 1.5` (24px), so *every* inter-block gap in Lectern was ~0.31em short of GitHub's, and a nested list — whose only separation from its parent item is the line-height — had no gap at all. `LINE_HEIGHT`/`line_leading()` supply the difference from **live font metrics** at both ends (`decorated_textview.py`'s Pango context, `printing.py`'s own possibly-substituted font), never as a constant, since it depends on the font and must track zoom. It hangs on the always-on `prose` tag as **`pixels-below-lines`, not above**: a block gap is a `pixels-above-lines` tag on the same line, two tags setting the *same* property don't add (highest priority wins), and below+above are different properties and do add.
- `decorated_textview.py` — the `Gtk.TextView` subclass the window actually uses. `Gtk.TextTag` cannot draw a *box*: `background-rgba` hugs the glyph runs with no padding or corner radius, `paragraph-background-rgba` adds no vertical padding either, and there is no border property at all. So the h1/h2 bottom rule, the inline-code chip and the fenced-code panel are painted in `snapshot()` with Cairo, under the text, from rectangles found via `get_iter_location()`. It also owns the **content column** (`_sync_metrics`, called from `do_size_allocate`): its own four margins, and the tag margins that have to move with them. **A `Gtk.TextTag` left-margin *replaces* the view's rather than adding to it** (probed empirically), so every tag spelling out an indent — lists, blockquotes, fenced code — is positioned from the window edge. Capping the measure at `MAX_MEASURE_EM` by growing the view's margins alone would centre the prose and leave all of those pinned to the left (#5). Two more things to know before touching it: **`Gtk.TextIter` is mutable and `forward_to_tag_toggle()` edits it in place** (handing the walk's own iter out as a range end once made every chip grow to swallow the rest of the document — hence the `.copy()` calls and the regression tests), and **drawing outside the text box does not create the space it needs** — the padding constants in `tags.py` are paired with layout that reserves room for them (`heading{1,2}`'s `pixels-below-lines`, and `renderer.py`'s `_BLOCK_PADDING` for fences).
- `tables.py` — table subtree → `Gtk.Grid` (screen) + row-text extraction (print). Column widths are weighted by *median* character length per column (`column_char_weights`), shared by both the on-screen `Gtk.Label.max_width_chars` hint and print's proportional pt-width split — one heuristic, not two independently-tuned ones. Median, not mean/max, so one outlier cell doesn't blow out its column.
- `highlighting.py` — Pygments wrapper mapping token types to a small fixed set of `pyg-*` tag names (defined in `tags.py`).
- `mermaid/` — ```mermaid fences, parsed and drawn here rather than by a browser. The backend choice is the same one the rest of the app makes: mermaid-cli needs Node plus a headless Chromium (unavailable in the Flatpak, hundreds of ms per diagram) and a remote render service would post the document to a third party on open, which `images.py` refuses to do for images. A parser per diagram family (`flowchart.py`, `sequence.py`, `entities.py` for `classDiagram`/`erDiagram`) turns source into a model, and the model into a `scene.Scene` of absolute geometry in the same nominal 96dpi pixels everything else measures in, with *role names* instead of colours (resolved by `tags.diagram_palette`, so one scene draws light, dark and on paper). `layered.py` is the shared graph layout — a cut-down Sugiyama: rank, order by barycentre sweeps, place by priority, dagre's shape without the solver — used by everything except sequence diagrams, whose vertical axis is just statement order. `draw.py` paints a scene with cairo; `view.py` is the anchored widget, `printing.py` the other caller. Four things that are load-bearing:
  - **Coverage is a subset, and the fallback is the design.** Anything unparsed raises `Unsupported` and `renderer.py` emits the fence as a highlighted code block. A diagram drawn from a half-understood source is worse than an honest listing, because a reader can't tell a mis-parse from what the author wrote. `subgraph` shows the shape of that bargain: the layout knows nothing about membership, so `_reserve_cluster_room` grows each member by the padding and title band its frames need *before* the layout runs (afterwards there is nowhere to put a frame that hasn't already got a node in it), and `_cluster_boxes` fits the frame to wherever the members landed. Nothing stops the layout interleaving two blocks' members, so a fitted frame that would enclose a node it doesn't own raises `Unsupported` rather than being drawn — a frame around a foreign node states a grouping the author never wrote.
  - **Text is measured with `set_absolute_size`, never `set_size`.** A point size is multiplied by the context's resolution — 96dpi for a window, 72dpi for a `Gtk.PrintContext` — so the same node would come out a third smaller on paper than the box laid out for it. Absolute sizes are in the target's device units, and print scales its context by `PX_TO_PT` so one device unit is one scene pixel. **And metric hinting is off** (`_unhint_metrics`, on both the measuring and the drawing side): hinted glyph advances round to whole *device* pixels, so they stop being proportional to the font size the moment a context is scaled — which `view.py` does to fit a diagram into the window. A label measured at 1.0 then re-wraps when drawn at 0.82, putting a third line in a box laid out for two.
  - **A scene is only valid for the font it was measured with**, so `PrintItem` carries the parsed *model*, not the screen's scene, and printing lays it out again in the print font (which differs — see `_base_font`). The measuring and the drawing both go through `text.make_layout` so no knob can drift between them.
  - Watch for cairo path hygiene: `PangoCairo.show_layout` leaves the preceding `move_to`'s current point behind, and `cairo_arc` *connects a line* from the current point to the arc it appends. That put a stray line across the first diagram that had a circle node in it; `draw.py` clears the path after every string.
- `images.py` — one `ImageView` per `![alt](src)`, anchored into the buffer like tables. **Remote (`http(s)`) images are deliberately not fetched on open** — that would let whoever hosts an image learn you opened the document, with a per-image URL working as a read receipt; `window.py` raises an `Adw.Banner` and only then calls `load_remote()`. Local paths resolve against the document's directory, the same base `_open_href` uses. Loading can't cascade: raster formats are self-contained and librsvg (verified on 2.60) drops *every* external reference — remote and local `href`, CSS `@import`, `<use>`, `@font-face`, `xi:include`. A Flatpak without `--share=network` is the real backstop for that, not the note. Images are excluded from `_fill_width_widgets`: they take the available width as a ceiling to scale down to, never a width to fill, and are never upscaled past their own pixels.
- `findbar.py` — `Gtk.TextIter`-based search over the buffer, *plus* a parallel scan of the table cells (whose text never enters the buffer). Cell matches are highlighted by re-rendering the cell's markup with background spans baked in, **not** via `Gtk.Label.set_attributes` — GTK merges those into the label's cached `PangoLayout` rather than replacing them, so a shrinking match set (backspacing in the find bar) leaves stale highlights painted. Both kinds of match merge into one list ordered by document position, so Next/Previous and the counter don't expose the split.
- `zoom.py` — one `Gtk.CssProvider` per window scoped via a unique CSS class (not per-widget `StyleContext.add_provider`, which is deprecated), stepping a font-size on the `TextView`. That covers half the job: heading/code tags carry static `Gtk.TextTag.scale` values GTK composes on top of it automatically, but every *absolute* length in `tags.py` (line spacing, block gaps, indents, margins) has to be re-scaled by hand through `DecoratedTextView.set_layout_scale` → `tags.apply_metrics`. Setting only the font-size, which is all this module originally did, left the layout correctly proportioned at exactly 100% and nowhere else (#6).
- `printing.py` — `Gtk.PrintOperation` pagination built from `print_model`, walking Pango layouts page-by-page. `Pango.AttrList` offsets are UTF-8 *byte* offsets, not character offsets — run-boundary byte lengths are computed explicitly, not assumed to match `len(text)`. `Pango.LayoutLine` keeps only a weak reference to its parent `Pango.Layout`, so the built `_Block` list must be kept alive in `state` between `begin-print` and `draw-page`, not just its derived page geometry.

  **Paper is meant to look like the screen**, so print takes its lengths from the screen's rather than inventing its own: every constant in `tags.py`/`renderer.py` is in nominal 96dpi pixels and reaches paper through `pt()` (×72/96), inter-block spacing rides along on `PrintItem.gap` from the renderer's collapsed-margin model, and the body font is pinned to GTK's UI font at `zoom.py`'s `BASE_PT`. Two traps behind that: pages are drawn a line at a time (`show_layout_line`, so a block can split across a page break), which discards every horizontal offset Pango computed for the line unless it travels with it — that's what `_line_geometry`'s `x_off` is for; and a *variable* UI font (the current GNOME default) cannot carry its own weights into a PDF, because cairo's font subsetting keeps only one weight pairing per face, so mixing regular and bold prints every heading above the first size in regular. `_base_font()` substitutes a static-faced family on paper only. Both were reproduced in plain Pango/cairo with no Lectern code involved; don't "simplify" either away.
- `filewatch.py` — `Gio.FileMonitor` with `WATCH_MOVES` (needed because editors that save via write-temp-then-rename otherwise look like the file vanishing) and a 300ms debounce coalescing the burst of events one logical save produces.
- `recent.py` — the recently-opened list, a thin wrapper over `Gtk.RecentManager.get_default()` (the desktop-shared store; no GSettings schema, and unlike a path-keyed file it survives the Flatpak document portal remounting the same file at a new path each open). Recorded in `window.py`'s `_open_file` after a successful load; shown on the empty-state page and in the headerbar's **Open Recent** submenu, both filtered to Markdown and to files that still exist. **`add_full`, not `add_item`** — `add_item` derives the registering app from `g_get_application_name()`, unset until a `GApplication` is running, so it silently no-ops (with a warning) from a script or a test.
- `window.py` — one `LecternWindow` per file; owns the widget tree, find-bar/zoom UI, click dispatch for links/footnotes (via `renderer.target_at_iter`), reload handling (preserves scroll position as a fraction, not an exact mark, since content may reshuffle), and the anchored-widget width sync described above. **The headerbar's `Adw.WindowTitle` is a widget, not the window's title** — setting it does nothing for `Gtk.Window`'s own `title` property, which is what the shell's window list and Alt-Tab read. `_sync_window_title` sets that separately (document's first h1, else the filename); without it every window reported no title and the shell listed them all identically as the application name. It's called from `_render_document`, so a reload that changed the heading retitles the window too.
- `main.py` — `Adw.Application` with `HANDLES_OPEN`. `do_open` creates one window per file, including on repeat launches while already running (GApplication's default D-Bus single-process activation still produces a new window, not a reused one — this is intentional, not an oversight). App-scoped accelerators (`window.close`, `app.quit`, zoom, find, print) are bound once in `do_startup`, not per-window — binding them per-`LecternWindow.__init__` would redundantly re-apply identical accelerator maps for every window opened.

**Testing:** most tests never realize or show a window, but they **do need a display** — `Gtk.Grid()` construction segfaults outright when there is none, which is why CI runs them under `xvfb-run -a`. On a desktop they just work, so this only bites in containers and CI.

`test_layout.py` is the exception, and the exception is load-bearing: it measures *rendered geometry* (`get_iter_location`/`get_line_yrange`) rather than tag properties, so spacing regressions fail a build instead of being argued about. Four things it had to establish, each of which silently produces plausible-looking numbers rather than an error when got wrong — verified in both a GNOME session and a `fedora:42` + Xvfb container:
- **`Gtk.Widget.allocate()`, not `realize()`, is what makes vertical geometry valid.** Without an allocation `x` and text height are still correct while `y` and `get_line_yrange()` are all 0, so every gap computes as 0 and the spacing looks perfect.
- **A CSS font-size only reaches a `TextView`'s layout once the window is *presented*.** The widget's Pango context reports the new size immediately, even unparented; the layout keeps the old metrics. `realize()` alone was enough on a desktop and **not** in the container, so the difference is not something a desktop run can catch.
- **With no window manager the window ignores its requested size** (a `default_width=700` window is allocated 640 under Xvfb), so tests force the width with an explicit `allocate()` *after* present — **twice**, either side of the event drain: the view sets its own margins from the width it is allocated, and servicing the resize that queues is exactly what lets the wrongly-sized toplevel allocate it back down again.
- **A live zoom change needs a real main loop iteration**; draining pending events does not do it, since the relayout arrives on a frame-clock tick.

Presenting a window means CI needs **`GSK_RENDERER=cairo`** — the default GL renderer aborts the process (SIGABRT, uncatchable) where there is no `libGLESv2`, which is the case with the packages CI installs. `tests/conftest.py` sets it as a default so a bare `podman run` can't core-dump the suite; `tests.yml` also sets it explicitly so the reason is visible where the failure would appear.

One test is the exception to "derive expectations from the constants": `test_block_pitch_matches_the_browser` asserts against `GITHUB_PITCH_EM`, real numbers measured in Chromium with `github-markdown-css` (render PROBE through markdown-it into a `.markdown-body` div, then read back one client rect per rendered line via a `Range` over each text node). Everything else checks Lectern's model; this checks the model lands where GitHub lands. Boundaries left out of that table are **recorded divergences, not oversights** — headings (GitHub gives h1–h6 `line-height: 1.25`, Lectern the font's own) and fences (font-size 85%, line-height 1.45).

Other assertions there are in **em, never pixels**, and expectations are derived from the constants in `tags.py`/`renderer.py` rather than pasted as measured numbers. Pixels are not portable across machines (the same heading measures 46px in Adwaita Sans and 51px in DejaVu Sans) while the em ratios agree to two decimal places. Character counts are not portable either — a 1600px window fits 90 characters of DejaVu and well over 100 of the narrower Adwaita, so "line too long" is asserted as a column width in em, not as characters per line.

Both of the layout bugs the harness was built for (#5 no maximum measure, #6 zoom doesn't scale spacing) started life there as **`strict=True` xfail** tests written the way the fix should behave; landing each fix turned it into a failure, which was the signal to delete the marker rather than the assertion. Those tests are now the acceptance criteria for both and assert *ratios*, not particular constants — `test_zoom_preserves_every_em_ratio` and `test_capping_the_measure_moves_the_whole_column_not_just_prose`. Same pattern for the next one.

**Do not "verify" headlessness by unsetting `DISPLAY` and `WAYLAND_DISPLAY`.** GDK falls back to the default `wayland-0` socket in `XDG_RUNTIME_DIR` and connects anyway, so the suite passes and looks headless while still talking to the compositor. This exact mistake led to CI being written without xvfb and segfaulting on both distros. To test it properly, also point `XDG_RUNTIME_DIR` at an empty directory.

Tests assert tag placement on parsed-and-rendered buffers (e.g., parse `"hello **world**"`, locate `"world"`, assert it has the `strong` tag) — this is the pattern to follow for new renderer coverage rather than snapshot-testing rendered output.

**CI** (`.github/workflows/`): `tests.yml` runs the suite on Ubuntu and in a Fedora container; `data.yml` validates the desktop entry and the SVGs. The two distros are there for the **GTK version** spread, not the Python one — a Python matrix is impossible anyway, since PyGObject is a system package carrying the typelibs and is pinned to the distro's Python. Both test jobs build the venv exactly as the README documents, so breaking the documented install breaks CI.

**App ID:** `io.github.osandum.Lectern` — permanent once published to Flathub, so don't churn it. The Python package/import name (`lectern`) and the GitHub repo name (`osandum/lectern`) are independent of it and don't need to match.

## Data files and packaging

`data/` holds the desktop entry and the icons (`icons/hicolor/scalable/apps/` for the colour icon, `icons/hicolor/symbolic/apps/` for the monochrome one, both named after the app ID).

**None of it is installed by `pip install -e .`** — `pyproject.toml` ships only the Python package, so for a plain pip install the desktop entry and icons have to be copied by hand (see the README). The **Flatpak manifest installs them explicitly** in its `build-commands`; if you add a data file, add it there too or it silently won't ship. `Exec=lectern %U` deliberately resolves via `PATH` rather than hardcoding a path into somebody's venv, which an earlier version did.

**Flatpak** (`build-aux/io.github.osandum.Lectern.yml`): GNOME runtime 50, which supplies PyGObject, GTK4, libadwaita, libsoup3 and librsvg — only the four pure-Python dependencies are built, from wheels pinned by URL and sha256 (a Flatpak build has no network). The manifest currently uses a `type: dir` source so it builds from a clone; **Flathub requires immutable sources**, so submission needs a git source pinned to a tag and commit. Two `finish-args` carry real justification and shouldn't be trimmed without thought: `--filesystem=host:ro` because the document portal grants only the opened file while Markdown resolves images and links *relative* to it, and `--share=network` because the remote-image banner has nothing to do without it. `--socket=cups` is deliberately absent on the theory that GTK4 routes printing through the portal when sandboxed — **untested in an actual sandbox**, and the first thing to try if printing turns out broken.

**Screenshots** (`data/screenshots/`) are generated from `demo.md` in that directory, and are referenced by the metainfo as raw.githubusercontent URLs, so renaming one breaks the metainfo. They are deliberately shot from a neutral path (`/tmp/lectern-demo/Documents`) rather than a home directory, since the headerbar shows the document's directory and these end up on a public store page.

**Icon constraints, learned by testing rather than assumed** — worth not re-litigating:
- The page is **portrait**. A landscape page above a stand reads as a *laptop* at 32px; four drafts failed this way before the shape was changed.
- The stand is **one flaring mass**, not a column and a foot. Thin slabs vanish at 32px and leave the page looking like a sign on a post.
- In the symbolic variant the page must be an **outline**. Filled, it merges into the stand and the silhouette becomes one blob.
- Always check a candidate at 32/48/64, not just at 128 — every one of the above only shows up small. Render through librsvg (what GTK uses), not ImageMagick's SVG delegate.
- `--` is illegal inside an XML comment, so the `--` used as a dash elsewhere in this codebase can't be used in the SVGs.
